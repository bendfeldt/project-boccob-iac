## Polaris [verified]

- Metastore: `relational-jdbc` on CloudNativePG cluster `polaris-db`
  (`sslmode=verify-full`); the schema is created by the bootstrap Job (Polaris
  1.9 no longer creates it). Realm `POLARIS` and the root principal are
  bootstrapped by `polaris-admin-tool bootstrap -f <credentials file>`; the root
  credentials are generated in-cluster and live in `kv/catalog/polaris/root`.
- Token signing key (symmetric, shared by all replicas): `kv/catalog/polaris/token-broker`.
  Polaris is stateless otherwise: `polaris_replicas` (HA: 2) + PDB + topology spread.
- Provisioning Job (`modules/polaris/files/provision.py`, idempotent): catalogs
  `raw|clean|consolidated|curated`, `default-base-location = s3://lakehouse-<layer>/iceberg`,
  `allowedLocations = [s3://lakehouse-<layer>/]`, storage `S3` with
  `stsUnavailable`, `pathStyleAccess`, `endpoint(Internal) = https://rustfs-svc.storage.svc:9000`,
  catalog property `polaris.config.drop-with-purge.enabled=true` (plus realm
  feature `DROP_WITH_PURGE_ENABLED`). Principals with their own principal role
  and one catalog role per catalog:

  | Principal | Catalog role grants | Used by |
  |---|---|---|
  | `trino` | `CATALOG_MANAGE_CONTENT` on all four | Trino Iceberg connector |
  | `ingest` | `CATALOG_MANAGE_CONTENT` on `raw` only | Dagster index stage (pyiceberg) |

  Privileges removed from the variable are revoked. Credentials are generated by
  Polaris and written by the Job to `kv/catalog/polaris/principals/<name>`
  (OpenBao policy of the Job: create/read/update on that prefix only). If a
  principal exists but OpenBao holds no valid credentials, they are rotated.
- S3: Polaris reads table metadata with the S3 user `lakehouse-catalog`
  (static credentials; RustFS has no STS, so credential vending is off and
  every engine brings its own S3 user: Trino `lakehouse-query`, Dagster
  `lakehouse-orchestration`).

**Authentication decision: Polaris-internal principals, Keycloak optional.**
Polaris 1.9.0 supports `internal`, `external` (OIDC, here Keycloak) and `mixed`
authentication (chart `authentication.type`, `oidc.*`; verified in the chart
values and configmap template of 1.9.0). Internal principals are used because
(1) the only Polaris clients are machines (Trino, the ingestion stage), which
need client-credentials with Polaris *principal roles*: with Keycloak tokens
the principal roles would have to be mapped from token claims for service
accounts that live in another system, and a Keycloak outage would stop every
query; (2) people never talk to Polaris directly — their authorisation is
enforced in Trino by OPA, which sees the real user, whereas Polaris only sees
the engine. `polaris_oidc_enabled = true` switches to `mixed` (client `polaris`
of the realm) for administrators who want Keycloak logins at the management
API [static].

  `TRINO_HOST=trino.<base_domain>`, `TRINO_PORT=443` (through Traefik like every

### Pseudonymisation pepper

Created once by the Job `dagster-pepper-*`: 64 random characters, written to
`kv/orchestration/pseudonym-pepper` (property `pepper`) with check-and-set 0.
The Job's OpenBao policy allows `create` but not `update`, so neither a re-run
nor a redeploy can replace an existing pepper; nothing is generated by
OpenTofu and the value is never logged. Losing the pepper breaks key
continuity (all pseudonyms change); leaking it weakens the pseudonymisation.

Backup: (1) it is part of every OpenBao raft snapshot (ops package,
`stacks/32-backup`); (2) additionally keep an offline copy in the key custody
store at initial deployment:
`bao kv get -field=pepper kv/orchestration/pseudonym-pepper` on a custodian
workstation into the sealed custody envelope (two copies, like the state
passphrase). Restore into an empty OpenBao *before* deploying stack 22:
`bao kv put kv/orchestration/pseudonym-pepper pepper=-` (value on stdin); the
Job then leaves it alone. KV v2 keeps versions: a mistaken write can be rolled
back with `bao kv rollback`. Never rotate without the re-index plan of the
solution (docs/gdpr.md there).

## TLS exceptions (audit M-3)

Every connection that leaves a namespace, and every client connection, is
TLS with certificates from the platform PKI. Three hops inside a namespace are
plaintext; each is confined by NetworkPolicy to the two pod groups involved:

| Hop | Protection | Why not TLS |
|---|---|---|
| Trino coordinator <-> workers, HTTP 8080 (`query`) | `internal-communication.shared-secret` (signed internal requests); policy `allow-in/out-trino-internal` (Trino pods only). dev runs **no workers** (`trino_workers = 0`), so the hop does not exist there | Trino's built-in internal TLS (`internal-communication.https.required`) only works with automatically generated certificates for IP addresses and an IP-based `discovery.uri`; the official chart (1.45.0) hard-codes `discovery.uri=http://<service>:8080`, and Trino has no configuration for an external key store for internal traffic |
| Dagster webserver/daemon -> code server, gRPC 4000 (`orchestration`) | policies `allow-in/out-code-server` (only Dagster system pods) | the chart and `dagster api grpc` have no TLS options for the code server |
| oauth2-proxy -> Dagster webserver, HTTP 80 (`orchestration`) | policies `allow-in/out-webserver` (only the proxy pods); the webserver has no other ingress | `dagster-webserver` cannot serve TLS |

In test/prod these hops can cross nodes. Mitigation **[static]**: test and
prod run flannel with `wireguard-native` (`K3S_FLANNEL_BACKEND` in
`environments/{test,prod}/env.sh`, rendered into the server configuration by
`scripts/lib/k3s-config.sh`, carried to the hosts in the node bundle), so all
pod traffic between nodes — these three hops included — is encrypted with
WireGuard. Requirements: WireGuard kernel module (Linux >= 5.6, in every
supported distribution kernel), UDP 51820 open between the nodes, the same
backend on all servers (it cannot be changed on a running cluster without
re-creating it). dev (single node, k3s in Podman) keeps the default vxlan
backend: there the hops never leave the node.

## Audit trail and personal data (audit H-1)

The Trino audit sink redacts string content that looks like a pseudonymised
subject key (64 hex characters) or a CPR number (`DDMMYY-NNNN`, `DDMMYYNNNN`)
in the query text before the record is written (`<redacted>`); the shape of
the query, user, groups, tables and columns stay. Unit tests:
`modules/trino/files/test_audit_sink.py` (run by `make lint`); verified live on
dev (a query with both kinds of literal is logged with `'<redacted>'`).
Trino's own query history (`system.runtime.queries`, in memory, visible to
`platform-admin`/`auditor` through OPA) still holds the text until it expires
(`query.max-history`); the solution should stop putting keys into SQL (audit
H-1, solution part).

## Purge credential and deletion safety window

The S3 user `lakehouse-purge` may delete object **versions** on the four lake
buckets: whoever holds it can destroy lake data beyond recovery. Since audit
N-3 it is handed only to the runs that need it:

- Secret `lakehouse-purge-env` (`PURGE_S3_ACCESS_KEY_ID`,
  `PURGE_S3_SECRET_ACCESS_KEY`; `modules/dagster` `job_secrets`, stack 22
  `purge_jobs` = `erasure`, `retention`, `iceberg_maintenance`). It is neither
  in `lakehouse-env` nor in the code server's container context, so ingestion,
  dbt and every other run start without it.
- A purge job attaches it with the Dagster K8sRunLauncher's per-job Kubernetes
  config (pinned dagster-k8s 0.29.30: tag `dagster-k8s/config`,
  `container_config.env_from`, merged DEEP with the code location's container
  context, lists appended). The Secret name is in `PURGE_ENV_SECRET`.
  [verified on dev: an `erasure` run launched with the tag got
  `envFrom: [user-env ConfigMap, lakehouse-env, lakehouse-purge-env]` and
  succeeded]
- Two built-in ValidatingAdmissionPolicies (always Deny, independent of the
  Kyverno mode; `orchestration-lakehouse-purge-env-job|pod`) admit a Job or Pod
  in `orchestration` that references the Secret (envFrom, env, secret or
  projected volume) only when its label `dagster/job` is one of `purge_jobs`
  **and** it comes from the run launcher (Job: ServiceAccount `dagster`, which
  the queued run coordinator uses for every launch) or the Job controller
  (Pod). Run pods' own ServiceAccount may create Jobs and Pods (chart RBAC), so
  without the creator rule a compromised ingestion run could mount the Secret.
  `make verify` checks all three cases with server-side dry runs.
- Residual: anyone allowed into the Dagster UI (`platform-admin`,
  `data-engineer`) can launch a purge job, including with extra run tags; that
  is the intended authority over erasure/retention/maintenance.

What the solution must add (not in this repository): on the jobs `erasure`,
`retention` and `iceberg_maintenance` (`orchestration/jobs.py`)

```python
PURGE_TAGS = {"dagster-k8s/config": {"container_config": {"env_from": [
    {"secret_ref": {"name": os.environ.get("PURGE_ENV_SECRET", "lakehouse-purge-env")}}]}}}

@dg.job(..., tags={"lakehouse/kind": "erasure", **PURGE_TAGS})
```

(Dagster serialises a dict tag value to JSON; the default multiprocess executor
runs every op inside the run pod, so no step-level config is needed). Until that
release is deployed these jobs run without `PURGE_S3_*`:
`S3Settings.for_purge()` then falls back to the ordinary credential and the
version deletes fail loudly (AccessDenied) instead of being skipped. A renamed
or additional purge job must be added to `purge_jobs`.

Delayed-deletion window: `lakehouse_noncurrent_version_days` (stack 12) is 7
days by default (was 1). Trade-off:

| | 1 day | 7 days (default) |
|---|---|---|
| erasure | no difference: the erasure deletes the versions of the objects it touched explicitly | same |
| retention / maintenance deletes (ordinary deletes) | final after 1 day | recoverable for 7 days, then final (state it in the retention policy) |
| accident (`DROP TABLE` with purge, faulty job, leaked non-purge credential) | 1 day to notice and undo | 7 days to notice and undo |

For the window to hold, the solution's maintenance and retention must not
purge **all** noncurrent versions: they should delete only versions older than
the window (`purge_noncurrent(..., older_than=...)`) or leave them to the
lifecycle; only the erasure purges the versions of its own objects at once.
The off-site lake copy keeps its own short expiry
(`offsite.lake.max_noncurrent_days`, stack 32).

## Erasure verification

`ERASURE_VERIFY_STORAGE=true` makes every erasure request read and decode
**every object version of all four lake buckets** (solution
`governance/erasure/storage_scan.py`, "O(size of the lake)"), while it holds the
`lakehouse_writer` pool. At test/prod size that blocks `daily_refresh` for hours
per request (audit N-1), so the switch is per environment:

| Environment | `erasure_verify_storage` | Why |
|---|---|---|
| dev | `true` | the synthetic lake is a few MB; every erasure is proven physically |
| test, prod | `false` | per-request whole-lake scan does not scale |

What still runs on every request (solution, independent of the switch): the
row counts of every plan step must be 0 afterwards (`verify_sql`), the subject's
raw files are deleted with all their versions, Iceberg history is expired and
the object versions of the affected objects are deleted explicitly. Separate
verification in test/prod:

1. **Periodic canary scan (test, monthly and after every release).** The
   synthetic source carries a fictional canary subject; the run submits its
   erasure and executes the erasure job with storage verification on (run
   config, see below) in a quiet window. A hit fails the run and pages
   through the Dagster failure alert. This proves the mechanism end to end on
   the same code and storage layout as prod, without keeping any real
   identifier for a later scan (the subject key is gone after the erasure, so a
   later whole-lake search for a real subject is impossible by design).
2. **Targeted scan on demand (prod).** For a request the DPO flags (e.g. a
   complaint), the erasure job runs with storage verification enabled for that
   run only, restricted to the object versions under the locations of the
   tables in the plan plus the subject's raw file paths, in a maintenance
   window outside `daily_refresh`.
3. **Off-site copy.** The lake copy follows the source within one mirror run
   plus the target's noncurrent-version expiry (stack 32, "Off-site copy and
   erasure"); a canary scan of the off-site target is part of the yearly DR
   exercise (runbook).

Solution side (not in this repository): a run-config flag on the `erasure`
job that overrides `ERASURE_VERIFY_STORAGE` for one run, and the targeted
scope of the scan (table locations + raw paths instead of whole buckets). Until
the flag exists, (1) runs in test by deploying stack 22 with
`erasure_verify_storage = true` for the window and back to `false` afterwards.
